# Insulator AI V5 — โครงการส่วนรวมผ่าน Firebase (ทดลองบนสาขาแยก)

> **ยังไม่ใช่ระบบใช้งานจริง**: ไฟล์ใน GitHub ไม่ได้เผยแพร่ Firestore Security Rules ไปยัง Firebase Console อัตโนมัติ ต้องตรวจสอบและทดสอบสิทธิ์ก่อนใช้ข้อมูลจริง
>
> การแก้ไขรอบนี้ **ไม่ลบข้อมูลเดิม** และ **ไม่ย้ายประวัติหรือภาพจากเครื่องขึ้นส่วนรวมโดยอัตโนมัติ**

## ฟังก์ชันระยะแรก

- กำหนดสิทธิ์ผู้ใช้ผ่าน Firebase Authentication + \`staffApprovals/{uid}\` ซึ่งผู้ดูแลเท่านั้นที่อนุมัติได้
- เจ้าของโครงการสร้าง \`sharedProjects/{projectId}\` จากชื่อโครงการในเครื่อง (ยังไม่มีประวัติ)
- เชิญสมาชิกด้วย UID ของบัญชีที่ลงทะเบียน Firebase แล้ว และกำหนดเป็น \`editor\` หรือ \`viewer\`
- เจ้าของ/ผู้แก้ไขสามารถส่งข้อมูลเสาและประวัติที่เลือกจากเครื่องไปส่วนรวม; **ไม่อัปโหลดภาพ**
- แสดงรายการโครงการ เสา ความคืบหน้ารายลูก และประวัติส่วนรวมแบบสดด้วย Firestore Snapshot Listener
- เมื่อบันทึกผลตรวจในเครื่องของโครงการส่วนรวม จะพยายามส่งผลใหม่ขึ้น Firestore โดยอัตโนมัติ ถ้าล้มเหลว ผลในเครื่องยังคงอยู่และสามารถส่งใหม่ด้วยปุ่ม "ส่งข้อมูลในเครื่อง"
- หมุดตำแหน่งผู้ใช้ GPS สดยังคงเป็นข้อมูลเฉพาะบนอุปกรณ์ ไม่ส่งเส้นทางติดตามขึ้น Firebase
- ข้อมูลส่วนตัวเดิมที่ \`users/{uid}/...\` ยังใช้สำรอง/ดาวน์โหลดแบบกดเองและไม่แชร์ข้ามบัญชี

## โครงสร้าง Cloud Firestore

\`\`\`text
staffApprovals/
  <uid>                 { active: true }    ← ผู้ดูแลสร้างผ่าน Firebase Console

sharedProjects/
  <projectId>           { id, name, office, prefix, description,
                          ownerUid, memberUids: [uid...],
                          members: { uid: "owner" | "editor" | "viewer" },
                          createdAt, updatedAt }
    poles/
      <encodedPole>     { projectId, pole, units, gps, updatedByUid, updatedAt }
    inspections/
      <recordId>        { id, projectId, pole, insulatorId, date, damage,
                          dirt, percent, inspector, status, units, remarks,
                          authorUid, imageInCloud: false, cloudUpdatedAt, ... }

users/
  <uid>/projects/...    ← ของเดิม ยังคงเป็นข้อมูลส่วนตัว
  <uid>/inspections/... ← ของเดิม ยังคงเป็นข้อมูลส่วนตัว
\`\`\`

## การเปิดใช้ก่อนทดสอบ

1. **สำรอง Firestore Rules ปัจจุบันจาก Firebase Console** เพราะ Repository ไม่สามารถอ่านกฎที่กำลังใช้จริงได้
2. ตรวจไฟล์ \`firestore.rules\` ในสาขานี้ **เปรียบเทียบและรวมกับ Rules เดิม** อย่าวางทับโดยไม่ตรวจว่ามี collection อื่นใช้งานอยู่หรือไม่
3. นำ Rules ไปตรวจ syntax และจำลองสิทธิ์ที่ Firebase Rules Playground หรือ Emulator ให้ผ่านก่อน Publish
4. ใน Firebase Console → Firestore Database → Data สร้าง document \`staffApprovals/<UID>\` และตั้งฟิลด์ \`active\` (boolean) เป็น \`true\` ให้ **เจ้าหน้าที่ที่ได้รับอนุมัติเท่านั้น**
5. ใช้บัญชีเจ้าหน้าที่นั้นล็อกอินเข้า V5 ในหน้า ตั้งค่า แล้วดู UID ที่แสดงในส่วน "โครงการส่วนรวม"
6. เลือกโครงการในเครื่อง กด "สร้างโครงการส่วนรวม" → จะสร้างเฉพาะข้อมูลชื่อโครงการ ยังไม่ส่งเสาหรือประวัติ
7. เปิดโครงการที่เพิ่งสร้าง กด "ส่งข้อมูลในเครื่องของโครงการนี้ขึ้นส่วนรวม" **หลังตรวจว่าข้อมูลที่เลือกอนุญาตให้แชร์แล้ว**
8. เชิญเจ้าหน้าที่อีกคนโดยกรอก Firebase UID ของเขา และเลือก editor/viewer; เจ้าหน้าที่คนนั้นต้องได้รับอนุมัติ \`staffApprovals\` เช่นกัน

> กฎสิทธิ์เป็นการป้องกันข้อมูลบนเซิร์ฟเวอร์ ไม่ได้เข้ารหัสหรือลบข้อมูลที่เคยบันทึกใน IndexedDB/localStorage บนอุปกรณ์ การใช้งานจริงควรเป็นอุปกรณ์ของเจ้าหน้าที่ที่เชื่อถือได้ และต้องเพิ่มระบบจัดการการล้างแคชบัญชีเมื่อออกจากระบบในระยะต่อไป

## ขอบเขต/ข้อจำกัดปัจจุบัน

- หน้ารายละเอียดส่วนรวมแสดงสดใน **ตั้งค่า → โครงการส่วนรวม** ก่อน แผนที่/ประวัติหลักยังใช้ข้อมูลที่เก็บอยู่ในอุปกรณ์ ไม่ใช่ข้อมูลส่วนรวมที่ฟังแบบสด
- บัญชี editor ที่ต้องการเพิ่มผลตรวจผ่านหน้าตรวจสอบเดิม ต้องกด "เพิ่มโครงการนี้ในเครื่องเพื่อสำรวจ" ก่อน (จะเก็บ metadata โครงการในเครื่อง) จากนั้นสร้าง/เลือกเสาและบันทึกผลตามปกติ
- สัญญาณออฟไลน์: การตรวจบันทึกลงเครื่องตามระบบเดิม แต่การซิงก์ส่วนรวมอาจล้มเหลวและต้องกดส่งใหม่
- ประวัติในหน้าส่วนรวมแสดง 500 รายการล่าสุดต่อโครงการเพื่อจำกัดการอ่านและค่าใช้จ่าย ยังไม่รองรับ pagination
- ขณะนี้ **ไม่ได้** เชื่อมภาพถ่าย Firebase Storage, ไม่เปิดประวัติส่วนรวมจากแท็บประวัติเดิม และยังไม่รองรับงานหลายเครื่องแบบออฟไลน์ที่ซิงก์สองทางโดยอัตโนมัติ
- การเผยแพร่แอปแบบ Public บน App Store ยังต้องวางกฎข้อมูล/สิทธิ์บนอุปกรณ์และตรวจความปลอดภัยเพิ่ม ห้ามถือว่า UI ซ่อนเมนูอย่างเดียวปลอดภัยเพียงพอ

## ต้องทดสอบอย่างน้อย

| สถานการณ์ | ผลที่ต้องได้ |
|---|---|
| ไม่ล็อกอิน | เปิดตรวจสอบ/แผนที่/ประวัติไม่ได้; หน้า login ยังเข้าถึงได้ |
| ล็อกอินแต่ไม่มี staffApprovals หรือ active=false | เปิดข้อมูลสำรวจไม่ได้ และ query sharedProjects ต้องถูก Rules ปฏิเสธ |
| เจ้าหน้าที่ A ที่ approved สร้างโครงการ | อ่านเขียนได้ในโครงการของตน |
| เจ้าหน้าที่ B ที่ approved แต่ไม่ได้ถูกเชิญ | ไม่เห็นหรืออ่านโครงการ A |
| เชิญ B เป็น viewer | B อ่านเสาและประวัติได้ แต่สร้าง/แก้ไขข้อมูลไม่ได้ |
| เชิญ B เป็น editor | B เขียนข้อมูลเสาและสร้างประวัติใหม่ได้ |
| ถอน B ออกจากโครงการ | B ไม่ควรอ่านจากเซิร์ฟเวอร์ได้อีก |
| บันทึกผลตรวจจาก A | B เห็นรายการใหม่ในแผงส่วนรวมโดยไม่กดดาวน์โหลด |
| ลบความเชื่อมต่ออินเทอร์เน็ตระหว่างบันทึก | ข้อมูลท้องถิ่นไม่สูญหาย มีข้อความแจ้งส่ง Cloud ไม่สำเร็จ |
| กลับไปใช้ V5 เดิม | Firebase ส่วนตัวและประวัติในเครื่องยังอยู่ครบ |

## หมายเหตุความปลอดภัยสำคัญ

- การสร้าง document \`staffApprovals\` ต้องทำโดยผู้ดูแลผ่าน Firebase Console/บัญชีที่มีสิทธิ์ ไม่เปิดให้ client สร้างได้
- อย่าคัดลอกกฎ \`allow read, write: if true\` มาใช้กับ \`sharedProjects\`, \`staffApprovals\`, \`users\` หรือพิกัดเสาไฟฟ้า
- \`firestore.rules\` ถูกเก็บใน GitHub เพื่อให้ตรวจสอบ source control ได้ **ไม่ใช่หลักฐานว่ากฎถูกเผยแพร่ขึ้น Firebase แล้ว**
- ก่อน Merge เข้า \`main\` ต้องยืนยันการ Deploy Rules และทดสอบ Firebase Emulator/Rules Playground กับบัญชีที่ถูกและไม่ได้รับอนุมัติ
- โครงสร้าง share แบบ UID ทำให้เจ้าของโครงการควบคุมการเชิญได้ แต่ไม่ได้รับประกันว่าผู้ที่ถือ UID เป็นเจ้าหน้าที่จริงจนกว่าผู้ดูแลจะตรวจสอบและอนุมัติ
